ТЕОРИЯ К БЛОКУ 1 — Docker с нуля

Не открывать до сдачи блока: это материал разбора, а не подсказка. Если прочитать раньше,
балл за блок перестаёт что-либо показывать.

Написано по сцене блока: те же команды, те же файлы, те же поломки. Каждая клетка
заканчивается шагом проверки — командой, которой правило видно своими глазами.
Docker не установлен? Проверять на play.docker.com (браузер, без установки) или после
установки Docker Desktop в PowerShell.

=== Клетка d1. Образ и контейнер ===

Образ — это набор слоёв только для чтения: база (python:3.12-slim), рабочая папка, твой код,
установленные пакеты, команда запуска. Слои не меняются: их можно только пересобрать заново.
Контейнер — это процесс, запущенный из образа, поверх которого Docker добавляет тонкий
записываемый слой. Всё, что приложение пишет во время работы, попадает именно туда.

Отсюда два разных удаления:
  docker rm -f app1     снимает контейнер вместе с его записываемым слоем
  docker rmi app:latest удаляет образ и его слои (и только если из него ничего не запущено)

После `docker rm -f 7c1a2b` образ app:latest остаётся на месте: он не принадлежал контейнеру,
контейнер был его запущенной копией. Поэтому `docker run app` снова поднимает рабочий
контейнер за секунду — слои уже собраны. Данные, которые были записаны внутри снятого
контейнера, при этом исчезают: они лежали в записываемом слое (см. клетку d6).

Проверка: `docker images` до и после `docker rm -f` — строка app:latest на месте;
`docker history app:latest` показывает ровно те слои, что были в Dockerfile.

=== Клетка d2. Порт: -p снаружи:внутри ===

У контейнера своя сеть. Порт, который слушает приложение внутри, снаружи не виден, пока его
не пробросят. Запись `-p 8000:5000` читается слева направо: 8000 — порт на твоём компьютере
(хосте), 5000 — порт внутри контейнера. Docker слушает 8000 на хосте и передаёт соединение
на 5000 внутри.

Поэтому браузер открывает `http://localhost:8000`, а `localhost:5000` даёт отказ соединения:
на хосте по этому порту никто не слушает. Приложение при этом живо и отвечает — но только
внутри контейнера.

Строка `EXPOSE 5000` в Dockerfile ничего не публикует: это подпись «приложение слушает 5000»,
по ней удобно строить команду запуска, но дверь наружу открывает только -p.

Если -p забыли совсем — приложение работает, а снаружи недоступно; это самая частая
«контейнер не отвечает», хотя контейнер жив.

Проверка: `docker run -p 8000:5000 app`, затем `curl http://localhost:8000` (отвечает)
и `docker exec app1 curl -s http://localhost:5000` (отвечает уже изнутри).
`docker port app1` показывает проброс: `5000/tcp -> 0.0.0.0:8000`.

Типичная ошибка: прочитать `-p 8000:5000` как «порт 8000 внутри, 5000 снаружи» и открывать
5000. Лечится правилом «слева — то, что нажимаешь в браузере, справа — то, что написано
в приложении».

=== Клетка d3. Слои и кэш сборки ===

Каждая инструкция Dockerfile создаёт слой. Docker считает для слоя отпечаток: текст инструкции
плюс содержимое файлов, которые в него попали. Отпечаток совпал — слой берётся из кэша.
Не совпал — слой пересобирается, и все слои ниже тоже: они зависят от предыдущих.

В исходном порядке `COPY . .` стоял до `RUN pip install`. Значит в слой копирования попадал
весь проект, включая изменённый файл кода. Менялась одна строка — менялся отпечаток COPY,
за ним сбрасывался pip-слой, и пакеты ставились заново (три из пяти минут сборки).

Правильный порядок: сначала то, что меняется редко.

  FROM python:3.12-slim
  WORKDIR /app
  COPY requirements.txt .            ← меняется раз в месяц
  RUN pip install -r requirements.txt ← слой держится в кэше
  COPY . .                            ← меняется каждый день
  CMD ["python", "app.py"]

Правило одной строкой: «что меняется чаще — ниже». Плюс `.dockerignore` (venv, __pycache__,
.git), чтобы мусор не менял отпечаток COPY и не раздувал образ.

Проверка: собрать, поправить строку кода, собрать снова — в выводе у pip-слоя будет `CACHED`,
сборка занимает секунды. Флаг `--no-cache` отключает кэш совсем: нужен, когда подозреваешь,
что кэш «залип», а не для обычной сборки.

=== Клетка d4. Контейнер завершился сразу ===

Контейнер живёт ровно столько, сколько живёт его главный процесс (PID 1 внутри). Процесс
закончился — контейнер остановлен, и `docker ps` его больше не показывает: без -a видны только
живые.

Три разные причины, и лечатся они по-разному:
  процесс упал — ошибка в коде, нет модуля, неверный путь к файлу; код возврата не 0;
  процесс отработал и вышел — скрипт без сервера, сервер ушёл в фон, запуск через
  `python app.py` без ожидания; код возврата 0;
  процессу не хватило условий — нет переменной окружения, файла, не хватает tty для
  интерактивной программы.

Порядок разбора поломки:
  docker ps -a                     увидеть контейнер, статус Exited (N) и код N
  docker logs app1                 увидеть traceback или пустоту
  docker inspect --format '{{.State.ExitCode}}' app1   точный код возврата

Код 0 при мгновенном выходе — это «отработал и закончил», ищи, почему сервер ушёл в фон.
Код 1 обычно означает исключение в Python: traceback в логах указывает строку.
Код 137 — контейнер убит (не хватило памяти или сработал docker kill).

Проверка: `docker run app` без -d, посмотреть, вернулось ли управление сразу; затем
`docker ps -a` и `docker logs`.

=== Клетка d5. CMD: shell-форма и exec-форма ===

Две записи выглядят как одно и то же, но запускают процесс по-разному.

  CMD python app.py          shell-форма: Docker запускает /bin/sh -c "python app.py"
  CMD ["python", "app.py"]   exec-форма: python запускается напрямую, без оболочки

В первом случае главным процессом контейнера (PID 1) становится sh, а python — его дочерним
процессом. Ctrl+C в терминале и `docker stop` (он посылает SIGTERM) попадают в sh. Оболочка,
получив сигнал, не обязана передавать его дальше: python продолжает работать, контейнер
висит, через 10 секунд Docker добивает его SIGKILL. Отсюда знакомое «нажимаю Ctrl+C —
ничего не происходит».

В exec-форме python сам PID 1, сигнал получает он, и останавливается штатно: закрывает
соединения, дописывает файлы.

Поэтому exec-форма — норма для приложений. Shell-форма нужна там, где осознанно нужна
оболочка: подстановка переменных, `&&`, пайпы.

Проверка: `docker exec app1 ps -o pid,comm` — в shell-форме первой строкой идёт sh, в exec —
python. Затем `docker stop app1`: в exec-форме контейнер гаснет мгновенно.

=== Клетка d6. Файлы и тома ===

Файл, созданный внутри контейнера, лежит в записываемом слое. Записываемый слой принадлежит
контейнеру, а не образу и не хосту. `docker rm -f app1` снимает контейнер — слой уходит вместе
с ним, база исчезает. Новая копия из того же образа стартует с чистым слоем: в образе лежал
только код.

Лечится подключением каталога с хоста:

  docker run -v C:/work/data:/app/data app     бинд-маунт: папка хоста внутрь
  docker volume create appdata && docker run -v appdata:/app/data app
                                                именованный том: Docker сам выбирает место

Слева — что на хосте, справа — куда это видно внутри контейнера. Путь внутри должен совпадать
с тем, куда пишет приложение (`/app/data`), иначе оно продолжит писать в свой слой, и данные
снова пропадут.

Том — не резервная копия, а место жительства данных: они живут на хосте, контейнер к ним
подключается, и пересборка образа их не трогает.

Проверка: запустить с -v, создать файл (или запись в SQLite), снять контейнер `docker rm -f`,
поднять заново с тем же -v — данные на месте. `docker inspect app1 --format '{{json .Mounts}}'`
показывает, что и куда подключено.

=== Одной фразой ===

Контейнер — процесс с упакованным окружением: жив, пока жив процесс; наружу виден только через
-p, а всё, что должно пережить его смерть, выносится на хост томом.
